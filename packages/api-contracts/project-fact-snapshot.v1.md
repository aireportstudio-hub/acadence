# Project confirmed-fact snapshot - service-to-service API v1

**Status:** P01 contract draft for review; not implemented or deployed.

## Chosen interaction

- **Caller:** AI Orchestration Service.
- **Owning service:** Project Service.
- **Purpose:** Read the latest confirmed project facts and their provenance for
  planning or generation. Project remains authoritative for confirmation;
  candidate observations are not included as confirmed facts.
- **Why this interaction:** The approved multi-agent architecture explicitly
  identifies "AI Orchestration to Project read confirmed fact snapshot" as a
  bounded synchronous HTTP call. This is a narrow read-only interaction that
  exercises service identity, scope, tenant checks, versioned DTOs, and request
  correlation without defining cross-service write or deduplication behavior.

## Proposed HTTP contract

The architecture's private API example is
`GET /internal/projects/{id}/fact-snapshot`. This draft adds an explicit `v1`
path segment to meet the P01 versioning requirement:

```http
GET /internal/v1/projects/{project_id}/fact-snapshot HTTP/1.1
Host: project-service
Authorization: Bearer <Google-issued audience-bound ID token>
X-Request-ID: req_p01_001
Accept: application/json
```

There is no request body. The identifiers and values below are illustrative,
not live Acadence project data.

### Successful response

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "project_id": "prj_example",
  "fact_snapshot_version": 7,
  "facts": [
    {
      "fact_id": "fact_example",
      "value": "example value",
      "provenance_ref": "answer_example"
    }
  ]
}
```

The `facts` array contains only confirmed facts. An empty array is valid when
the project has no confirmed facts. Callers must retain
`fact_snapshot_version` with any result derived from this response.

### Expected status codes

| Status | Proposed meaning |
|---|---|
| `200 OK` | Snapshot returned, including an empty snapshot. |
| `400 Bad Request` | Malformed path identifier or request metadata. |
| `401 Unauthorized` | Missing, invalid, expired, or wrong-audience service token. |
| `403 Forbidden` | Authenticated service lacks the required operation permission, or actor access is denied when the response does not reveal project existence. |
| `404 Not Found` | Project does not exist or is not visible to the authorized actor; do not reveal cross-tenant existence. |
| `429 Too Many Requests` | Caller or service rate limit reached. |
| `503 Service Unavailable` | Project Service or a required dependency is unavailable. |
| `504 Gateway Timeout` | The bounded read did not complete before its deadline. |

Errors generated by Project Service use the existing
[error response v1 schema](./error-response.v1.schema.json). This does not
define the error format for failures generated by AI Orchestration or another
service. Example of an error generated by Project Service:

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json
X-Request-ID: req_p01_001
```

```json
{
  "code": "FORBIDDEN",
  "message": "Request could not be completed.",
  "request_id": "req_p01_001",
  "details": {}
}
```

For this Project Service-generated error, the body's `request_id` matches the
`X-Request-ID` response header, as required by the existing README contract.
Error codes and messages above are examples; the shared schema does not
enumerate code values.

## Identity, authorization, and request correlation

- **Service identity:** The caller is the AI Orchestration Cloud Run service
  identity, authenticated to Project using a Google-issued, audience-bound ID
  token and least-privilege Cloud Run invoker permission. The token audience
  must identify the Project service. Cloud Run IAM authorizes the calling
  service. That service authorization does not establish a student's project
  access.
- **Application permission:** This draft proposes the narrow
  `project.facts.read` permission for this operation. Project Service must
  separately verify that the actor has access to the requested project and
  enforce the actor/project tenant boundary on every request. The mechanism
  for delegating actor context is open; do not treat a caller-supplied actor ID
  as proof. Deny access whenever Project Service cannot verify the actor's
  access.
- **Request ID:** AI Orchestration propagates the originating `X-Request-ID`
  unchanged. If this call starts a request without an ID, the first trusted
  service generates one and propagates it downstream. For errors generated by
  Project Service, the response `X-Request-ID` and error-body `request_id`
  must match and the body must conform to the shared schema. This error
  response guarantee does not apply to errors generated by AI Orchestration or
  another service. Trace context should be propagated separately when
  available.

## Retry and idempotency

This operation is read-only and has no idempotency key. The initial read
returns the latest confirmed snapshot available when Project Service handles
the request. Its `fact_snapshot_version` identifies that snapshot.

When a generation job accepts a snapshot version, that exact version is the
job's input for every retry and resume. Do not substitute a newer snapshot
within that job. If the accepted version cannot be recovered, stop the job;
do not continue with the latest snapshot. If newly confirmed facts require a
different version, bind that version explicitly to a new job rather than
silently changing the existing job's input. The storage and retention design
for recovering snapshots remains open. No write or mutation is performed by
this endpoint.

### AI Orchestration handling

- **Retry:** Retry bounded, transient failures such as timeouts, `429`, and
  temporary `5xx` responses, respecting retry guidance and preserving completed
  work. Before a job accepts a version, a repeated initial read may return a
  newer latest snapshot. After acceptance, every retry and resume must use the
  accepted version.
- **Stop:** Stop on non-retryable request, authentication, or authorization
  failures; when bounded retries are exhausted; or when the accepted snapshot
  version cannot be recovered. Surface the actual failure; do not retry
  indefinitely or fall back to a different snapshot.
- **Ask the student:** If required project facts are missing, unconfirmed, or
  contradictory, do not invent them or retry generation as if they were
  available. Ask the student through the Mentor and require confirmation via
  Project Service. If that confirmation creates a different snapshot version,
  use it only after explicitly binding it to a new job.

## Decision status

### Agreed architectural direction

- Project owns confirmed project facts; other services read them through an API
  or projection and do not write Project's data.
- AI Orchestration to Project confirmed-fact snapshot is an explicitly named
  synchronous interaction. Internal service calls are bounded and apply
  service identity, caller scope, tenant checks, typed DTOs, and correlation.
- For Cloud Run-to-Cloud Run calls, the architecture selects a Google-issued
  audience-bound ID token and least-privilege `roles/run.invoker` as the
  direction. This is an approved architecture direction, not a deployment or
  proof-of-concept claim.
- The package README and schema define the shared v1 error body shape and
  response-header/body request-ID matching rule. This contract applies them
  only to errors generated by Project Service.

### Proposed in this contract for review

- The exact versioned path, JSON field names, status semantics, and the
  `project.facts.read` permission name.
- Returning the latest confirmed snapshot on the initial read and pinning the
  accepted `fact_snapshot_version` for a generation job's retries and resumes.
- Mapping inaccessible projects to `404` to avoid exposing cross-tenant
  existence.

### Open decisions / implementation blockers

- Approve the exact route, DTO, permission vocabulary, error-code mapping,
  timeout/rate limits, and snapshot consistency behavior before implementation.
- Decide and verify the actor-context delegation mechanism. Cloud Run IAM
  authorizes the calling service but does not prove the actor's project access;
  Project Service must deny access if it cannot verify that access.
- Decide how accepted snapshot versions are stored, retained, and recovered.
- The architecture's Cloudflare Worker-to-Cloud Run ingress method remains
  unresolved pending proof of concept. This contract is specifically an
  internal Cloud Run service-to-service call and uses the selected Cloud Run IAM
  direction; it does not make the Project route a Worker-facing endpoint. Any
  Worker/BFF call path to Cloud Run must wait for the ingress decision and
  verification.
- Confirm service-to-service IAM behavior and denial of unauthorized calls in
  the target environment; the approved architecture and P00 compatibility
  record do not claim this is already proven.
